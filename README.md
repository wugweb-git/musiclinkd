# MusicLinkd

MusicLinkd is a professional network and marketplace for the music industry, with a customer-facing mobile app, public website, internal operations portal, and a shared design-system reference.

## Repository map

| Directory | Purpose |
| --- | --- |
| `frontend/guide/` | The design system. `index.html` is the live catalogue at `/guide`, generated by `scripts/build-guide.mjs`; `system/` holds the three stylesheets and `tokens/tokens.json` is the token source of truth. |
| `frontend/website/` | Public marketing website, and the image library under `assets/img/` that both the website and the guide draw from. |
| `webapp/` | The screen preview served at `/preview` — flow-by-flow HTML built by `scripts/write-screen.mjs` from the specs in `scripts/screens/`. Consumes the guide's stylesheets directly. |
| `admin/` | Internal operations portal; separate from the customer app. See [admin/README.md](admin/README.md). Also holds the canonical architecture docs the guide reads (`Widget_Directory.md`, `Master_Data_Seed_Values.md`). |
| `docs/` | Product, business, architecture and engineering documentation, plus `docs/handoff/` — the generated Compose token file for the native apps. |
| `backend/` | Backend/API foundation and future service layer. |
| `scripts/` | Every generator and audit. Nothing under `frontend/guide/system/ml-tokens.css`, `frontend/guide/index.html` or `docs/handoff/` is hand-edited. |
| `guide/` | Holds `docs/hardcoded-content-audit.md` only. Not the design system — that is `frontend/guide/`. |
| `archive/` | Deprecated or superseded artifacts retained for reference only. |
| `infrastructure/` | Hosting, domain, deployment, and infrastructure documentation/configuration. |
| `dist/` | Build output from `scripts/build-hosting.sh`. Gitignored; never edited directly. |

There is no `app/` directory: the Android application was moved to its own
repository (`1620e46`). It consumes this repo's output through
`docs/handoff/MusicLinkdTokens.kt`, not by sharing source.

## Design system and UI governance

The design system is the UI source of truth. Before adding or changing a UI surface:

1. Check the existing system components, tokens, patterns, and documented flows.
2. Reuse an approved equivalent whenever one exists.
3. Do not introduce a duplicate component, token, card, or page pattern without documenting why.
4. Keep product UI, brand-expression assets, and implementation details aligned with the canonical system.

The design-system catalogue is generated from the repository rather than maintained as an independent hand-written component inventory. The build entry point is [`scripts/build-guide.mjs`](scripts/build-guide.mjs).

### Generators

| Command | Writes |
| --- | --- |
| `node scripts/build-tokens.mjs` | `frontend/guide/system/ml-tokens.css` and `webapp/shared/ml-tokens.css` from `tokens.json`. Fails over the token-count ceiling or a scale past 4 steps. |
| `node scripts/build-guide.mjs` | `frontend/guide/index.html`. |
| `node scripts/build-handoff.mjs` | `docs/handoff/MusicLinkdTokens.kt` for the native apps. |

### Audits

Each one exists because the thing it measures was previously asserted rather
than checked, and the assertion was wrong.

| Command | Answers |
| --- | --- |
| `node scripts/audit-screens.mjs` | Do the preview screens resolve every token, link and class, and are they free of local `<style>` blocks? |
| `node scripts/audit-tokens.mjs` | Is any token dead, and does any stylesheet still write a literal where a token already names that value? Splits web-dead from native-only, because `--gesture-*` and `--component-*` are consumed by Compose, not CSS. |
| `node scripts/audit-guide-migration.mjs` | What did the superseded `styleguide.html` carry that the current guide still does not? Renames are aliased explicitly, so the count reflects real gaps rather than renamed sections. |

Every component in the catalogue also carries a **state map** — which of the
ten states it owns, inherits from the base layer, composes from another
component, or genuinely lacks. It is derived from the stylesheets, not listed
by hand. Absent states are shown struck through on purpose: a screen author who
can see that a component has no error state is told to build it in
`ml-widgets.css` rather than fork a second screen, which is how the flows
previously grew one screen per state.

## Product surfaces

| Address | Purpose | Source |
| --- | --- | --- |
| `musiclinkd.com` | Public marketing website | `frontend/website/` |
| `musiclinkd.com/guide` | The design system | `frontend/guide/index.html` |
| `musiclinkd.com/preview` | Screen preview, flow by flow | `webapp/` |
| `admin.musiclinkd.com` | Internal operations portal | `admin/` |
| `api.musiclinkd.com` | Reserved future API | `backend/` |

All of the above are served by a **single** Firebase Hosting site
(`musiclinkd-7ae30`). Hosting cannot route by hostname within one site, so
`musiclinkd.com` and `admin.musiclinkd.com` serve identical content — admin's
pages live at paths such as `/dashboard`, not at the admin domain's root. See
[infrastructure/firebase-hosting.md](infrastructure/firebase-hosting.md).

`/guide/styleguide` and `/guide/musiclinkd-system` are the superseded
catalogues and 301-redirect to `/guide`.

See [infrastructure/domains.md](infrastructure/domains.md) for deployment ownership and DNS requirements. These hostnames are documented product surfaces; source configuration alone does not mean a hostname is currently deployed.

## Backend and Firebase

MusicLinkd currently uses the Firebase project `musiclinkd-7ae30` across the Android app, website, and admin surfaces.

Repository-level Firebase configuration includes:

- `firebase.json`
- `firestore.rules`
- `firestore.indexes.json`
- `storage.rules`

## Hardcoded content rule

User-visible UI copy belongs in Android resources rather than Compose literals. Demo/seed entities belong in seed providers. Real runtime values belong to application state, repositories, or the database.

The recovered hardcoded-content audit is maintained at [`guide/docs/hardcoded-content-audit.md`](guide/docs/hardcoded-content-audit.md). Treat it as an audit and migration backlog, not as proof that every listed hotspot still exists unchanged in the current source tree.
