# Firebase Hosting — MusicLinkd

Project: **`musiclinkd-7ae30`**. **One** Hosting site (the project's default site,
also named `musiclinkd-7ae30`), with **two custom domains** attached to it:

| Domain                  | Serves                                                    |
| ------------------------ | ---------------------------------------------------------- |
| `musiclinkd.com`         | Marketing site (`website/`) — home, footer, legal pages    |
| `admin.musiclinkd.com`   | Admin app (`admin/`) — go directly to `/login` or `/dashboard` |

Both domains serve the **exact same deployed content** — Firebase Hosting has no
mechanism to route by hostname within one site (verified against
`firebase.google.com/docs/hosting/full-config`: rewrites only match on URL path,
never on domain). That's fine here because the two apps' routes don't collide:
website owns `/`, `/about`, `/pricing`, `/legal/*`, etc.; admin owns `/login`,
`/dashboard`, `/users`, etc. Visiting `admin.musiclinkd.com/` shows the marketing
homepage (same content either domain), and `admin.musiclinkd.com/login` /
`/dashboard` work identically on both — that's an accepted tradeoff, not a bug.

## Build

There is no single `public` source directory — `website/` and `admin/` are
separate source trees, merged into a build-only `dist/` at build time:

```bash
./scripts/build-hosting.sh
```

This builds `admin/` (Next.js static export → `admin/out/`) and merges it with
`website/` into `dist/`, which is what `firebase.json`'s `hosting.public` points
at. Two real collisions exist between the two source trees — both `index.html`
(root `/`) and `404.html` — and `website/`'s versions always win (see the script's
own comments for why: admin's root page is an unreachable auth-redirect shell in
this merged model, not something visitors land on). `dist/` is gitignored and
regenerated by the script — it should never be edited directly or committed.

Config lives in [`firebase.json`](../firebase.json) and [`.firebaserc`](../.firebaserc) at the repo root.

## One-time setup

> Do **not** run `firebase init` — `firebase.json` and `.firebaserc` are already
> committed, and init would overwrite them.

```bash
firebase login
```

No second Hosting site to create — the single default site already exists with
the project.

## Deploy

```bash
./scripts/build-hosting.sh
firebase deploy --only hosting,firestore,storage,remoteconfig
```

Preview channel (temporary URL, expires in 7 days) — build first, same as above:

```bash
firebase hosting:channel:deploy preview
```

## Custom domains

Add each domain in the Firebase console under Hosting → this one site → Add
custom domain, then create the DNS records it shows in your existing DNS
provider. Nameservers stay where they are — only records are added.

Firebase uses **A records only** — CNAME is not a supported way to point a custom
domain at Hosting, at the apex or on a subdomain. The TXT value is unique per
**site** (not per domain) — since both domains now attach to the same one site,
both TXT records use the same `hosting-site=...` value, shown in the console.

**musiclinkd.com** (apex)

| Type | Host | TTL  | Value                             |
| ---- | ---- | ---- | --------------------------------- |
| TXT  | `@`  | 3600 | `hosting-site=musiclinkd-7ae30`   |
| A    | `@`  | 3600 | `199.36.158.100`                  |

**admin.musiclinkd.com**

| Type | Host    | TTL  | Value                             |
| ---- | ------- | ---- | --------------------------------- |
| TXT  | `admin` | 3600 | `hosting-site=musiclinkd-7ae30`   |
| A    | `admin` | 3600 | `199.36.158.100`                  |

**www.musiclinkd.com** — add `www` as a third domain on the same site and choose
the redirect-to-apex option, then point it with an A record the same way.

If the console shows a second A record IP (some projects are issued a pair), add both.

### Rules that break SSL provisioning if ignored

- Remove any existing A, AAAA, or CNAME records on `@` and `admin` that point at another
  host. Firebase cannot issue a certificate while a conflicting record exists.
- **Keep the TXT records permanently.** They're not just an initial ownership check —
  Firebase requires them present to authorize SSL certificate renewal, for each domain.
- Leave any existing MX, and unrelated TXT records (SPF/DKIM) alone — mail is unaffected.
- Certificate provisioning runs automatically once the A records resolve; allow up to 24h.
- `https://musiclinkd.com/` and `https://admin.musiclinkd.com/` both get free,
  auto-renewing SSL from Firebase once each domain shows "Connected" — nothing
  to configure beyond the DNS records above.

### If the domain is behind Cloudflare

Set the proxy status to **DNS only** (grey cloud) until Firebase reports each domain as
Connected, otherwise certificate provisioning fails.

### Verify propagation

```bash
dig +short musiclinkd.com A
dig +short admin.musiclinkd.com A
dig +short musiclinkd.com TXT
dig +short admin.musiclinkd.com TXT
```

### Verify SSL after deploy

```bash
curl -vI https://musiclinkd.com/ 2>&1 | grep -i "SSL certificate\|subject:"
curl -vI https://admin.musiclinkd.com/ 2>&1 | grep -i "SSL certificate\|subject:"
```
